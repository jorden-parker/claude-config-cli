## Dependencies and boundaries

Default order: **001 → 002 → 006 → 003 → 004 → 005**. Plan 006 is small and only touches `internal/snapshot` and the README; running it first gets the uncommitted feature into a committable state before 004/005 edit the same README. Plan 003 is independent and can use a separate worktree. Serialize work on the shared store/status/TUI files unless integration is explicitly coordinated.

Plan 005 requires 001's load protection, 002's no-execution asynchronous activation, and 004's staged replacement boundary. Inside 003, extraction/validation must be repaired before regenerated output is published. Do not work around a missing predecessor by duplicating its implementation.

Plan 005 includes only the staging needed to make conflict rejection safe, overlapping part of deferred finding 8. It does not promise strict compare-and-swap against external writers: a documented final-check-to-rename window remains. Status activation continues to update two files separately, with honest partial-failure reporting. Plan 004 preserves existing final symlinks by replacing their referents and documents hard-link/extended-metadata limitations.

Effort estimates increased where detailed planning exposed required integration and filesystem cases. These are executor estimates, not time already spent implementing.
